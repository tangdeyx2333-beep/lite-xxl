# 无痕退出后仍恢复上次窗口现场

## 问题现象

打开“无痕退出”后关闭窗口，再次启动应用时，上次的窗口/标签页仍会恢复。无痕模式的预期是本次运行产生的临时恢复现场不应在下次启动出现。

## 调查结论

### 根本原因

当前“无痕退出”主要阻止后续写入，但没有在普通窗口退出时清理此前已经写出的临时恢复数据。定时保存与退出保存共享 `commit_realtime_instance_snapshot()`；无痕开启时该函数直接返回，因而退出路径不会覆盖快照，也不会清除旧快照。`core.exit(force)` 对无痕分支只记录“跳过保存”，随后清理的是普通临时文件，并未调用当前实例快照清理函数。

启动恢复会扫描 `unsaved_instances/instance_*.lua` 并恢复找到的快照，因此，只要无痕开启之前定时保存已经生成快照，退出后该文件仍在，下次启动就仍可能恢复原窗口。这与“无痕模式阻止后续保存”不等价于“无痕退出删除本次已有临时现场”。

### 需要一并纳入的临时数据

- 普通文档内容位于 `storage/ws/<snapshot_id>_doc_*`，实例快照引用这些键。已有的 `remove_runtime_instance_snapshot()` 已能按 `snapshot_id` 删除这两类文件，但普通强制退出的无痕分支没有调用它。
- WLPT 修改恢复数据由 `WlPtSession:persist_recovery_state()` 写入 `storage/wlpt/`，由独立的 `.meta`、`.snapshot`、`.add` 文件组成。定时提交可以写入这些恢复文件；现有实例清理函数不处理它们。文档关闭流程在脏状态时还会再次持久化恢复状态，因此仅在定时提交入口跳过保存仍不足以保证退出后清理完整。
- `workspace.lua` 在无痕状态下会跳过工作区写入，但已有的工作区记录不会因此被删除。它是另一条可能恢复标签页/布局的持久化链路，需要判断其数据是否属于本次无痕现场，并避免删除其他窗口或历史合法工作区数据。
- `session.lua` 的写入同样会被无痕状态阻止，但旧文件会保留。它记录最近项目及窗口参数；目前证据不足以将它认定为本次恢复标签页的直接来源。

## 代码证据

- `data/core/init.lua:633`：统一实时快照提交入口。
- `data/core/init.lua:643-651`：无痕开启时，提交直接跳过并返回，没有清理已有快照。
- `data/core/init.lua:546-587`：已有实例清理函数按实例 ID 删除 instance 快照及对应 `ws` 文件，但不处理 WLPT 恢复文件。
- `data/core/init.lua:855-859`：普通退出保存复用实时提交入口。
- `data/core/init.lua:1996-2024`：强制退出时无痕分支跳过快照保存；之后调用的是普通 `.lite_temp_*` 文件清理，没有清理实例恢复现场。
- `data/core/init.lua:1055-1075`：启动时扫描 `instance_*.lua` 并恢复快照。
- `data/core/init.lua:2776-2780`：主循环按配置周期调度实时保存。
- `data/core/doc/wlpt_session.lua:679-780`：WLPT 恢复文件路径、写入及清理三件套逻辑。
- `data/core/doc/wlpt_session.lua:1827-1853`：关闭 WLPT 文档时，脏文档会持久化恢复状态。
- `data/plugins/workspace.lua:222-247`：无痕模式跳过工作区写入，但不会消费或删除既存工作区记录。

## 建议修复方案

1. 把无痕退出定义为“本实例退出时不留可供下次启动恢复的临时现场”，而不是只阻止退出时新增写入。
2. 在退出流程收尾阶段，复用现有按 `snapshot_id` 清理 instance 与 `ws` 的能力；覆盖普通关闭、强制退出、最后标签页关闭及重启路径。清理前必须先从共享运行态同步无痕状态，避免多窗口状态刚切换时使用旧值。
3. 为 WLPT 增加可复用的恢复数据清理入口，按当前实例实际持有的文档精确清理 `.meta`、`.snapshot`、`.add`，并确保文档关闭逻辑不会在清理后再次把恢复数据写回。不要通过清空整个 `storage/wlpt/` 目录来实现，以免影响其他窗口/文档。
4. 核对工作区持久化的数据归属和消费时机。只有能证明属于当前实例且不会被其他窗口共享的数据，才纳入无痕清理；不能按“所有工作区记录”或“所有临时目录”做全局删除。
5. 在清理前后写中文流程日志，至少记录退出来源、无痕状态、实例 ID、目标文件类别、删除结果/失败原因，以及 WLPT 文档标识。便于区分“跳过写入”“清理成功”和“清理失败”。

## 验收场景

1. 普通文档已产生定时快照后开启无痕并正常关闭，再启动不恢复该实例标签页。
2. WLPT 文档产生恢复三件套后开启无痕并关闭，再启动不恢复未保存修改；其他窗口的 WLPT 恢复数据仍在。
3. 无痕开启后继续编辑，定时调度和退出过程都不生成可恢复现场。
4. 无痕关闭时保留原有定时保存和异常退出恢复能力。
5. 无痕期间关闭最后一个文件标签页、强制退出和重启均执行正确清理；不误删其他实例的恢复文件。
6. 验证工作区和 `session.lua` 不会在残留旧数据时绕过无痕语义恢复本次现场。

## 验证边界与后续日志

上述生命周期缺口可由当前代码静态确认。2026-10-17 20:07 的日志中，启动扫描到 3 份实例快照并恢复 14 个文档；同一轮退出记录显示无痕状态为关闭，工作区恢复未命中。用户确认界面当时显示无痕已开启，说明界面状态与日志中的共享运行态不一致，不能仅凭界面文字确认状态文件写入成功。

基于上述日志结果，修复在定时保存首次发现无痕状态时立即清理当前实例已有的 `instance/ws` 快照，并清理当前窗口持有的 WLPT 恢复三件套；强制退出时复用相同清理流程。强制退出只同步并判定一次保存策略，避免同一次退出过程中状态变化造成快照与 session 保存决策不一致。文档关闭时也按统一保存策略决定清理或持久化，避免 WLPT 恢复数据在退出收尾阶段被重新写回。
